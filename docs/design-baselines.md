# 设计基线与机制回归

## 当前边界

本规则自 2026-10-03 起适用。用户可以主动调整玩法、数值与关卡；旧测试的预期值是可审查的验收基线，不能据此否决已授权的设计变化，也不能为了绿灯反向覆盖用户已保存的新配置。本轮仅整理基线和测试职责，速度 56 px/s、短/长跳 16/40 px、训练场与三房间坐标均不改。

`tests/baselines/design-v1.json` 是测试独立维护的数据，记录来源提交、规则出处与基线身份。`unit_and_jump`、`walk_speed`、`room_graph` 来自已采纳规则；具体灰盒坐标是已交付样例的布局基线，**不表示用户已验收这些坐标或手感**。用户的新设计指令可以批准替换对应基线；尚无新指令时保留当前数据。

这份 JSON 不是游戏运行配置。生产代码和场景不得读取它，测试读取器也不读 `GameUnits`、`Player` 的属性、`.tscn` 或 `.tres` 来生成期望。它随 `tests/` 进入每轮真实工程快照并被 source SHA-256 覆盖。既有测试名称是 manifest 的稳定标识，其中的 `56`、`16_to_40` 等历史字样不代替 JSON 的生效基线；确需更名时人工同步 manifest，禁止从失败结果自动删减名册。

## 两类证据

| 类别 | 回答的问题 | 当前例子 | 有意调参时的处理 |
| --- | --- | --- | --- |
| `DESIGN_BASELINE` | 当前正式配置与已采纳规则/样例布局是否一致？ | 独立预期 56 px/s、16/40 px 跳高、身体尺寸、地形矩形、房间边界/入口、路由、相机 zoom | 先保留失败，核对新指令，再审查基线 diff |
| `MECHANISM` | 实际输入、物理、状态与配置边界是否按契约工作？ | 位移等于独立观测的速度积分、方向对称与停止、短/中/长跳排序、松键后重按不恢复上升、重置/恢复不残留跳跃状态、真实墙/顶接触、失效连接原子回退、跨房状态保留 | 保留断言；配置变化影响测试操作时调整受控输入/夹具，并解释原因 |

机制检查不只断言“某个对象的值等于从该对象读出的值”。例如速度用例同时核对独立设计速度，以及真实 60 个物理帧中的位移与开始时观察到的速度积分；状态恢复用例比较正常短跳与恢复后的新短跳，设计用例另校验正常短跳确实符合独立预期。配置变成零运动或坏跳跃时，方向/停止、真实起跳、跳高排序及设计检查仍提供失败证据。

一个 GUT case 可同时覆盖两类条件；为保持既有 manifest 与报告连续性，本轮没有拆分或跳过任何 case。数值断言的错误信息使用 `DESIGN_BASELINE:`，机制断言使用 `MECHANISM:`；源码注释与下表定位类别。GUT 的 JUnit 可能只保留某个失败 case 的第一条断言信息，分类时必须同时核对原始 GUT 日志中的失败断言；不得因 XML 首条是设计差异就忽略同一 case 后面的机制失败。分类只辅助定位，不改变原始通过/失败结果。**完整 game 验收始终执行两类检查**，定向运行不能代替完整回归，headless 通过仍不能代替用户手感反馈。

| 文件 / case 范围 | 类别 |
| --- | --- |
| `test_unit_scale.gd` 的尺寸、外框、速度、短/中/长跳、真实键盘短/长跳 | 混合：JSON 独立数值 + 实际物理/输入关系 |
| `test_unit_scale.gd` 的重按、落地不连跳、重置/失活恢复、缓冲、土狼窗口、撞顶、同帧松按 | 机制；JSON 中出生点/身体尺寸只作为明确的受控夹具布局，窗口与输入操作仍独立维护 |
| `test_map_world.gd` 的三房间/路由、边界/台阶、安全入口、旅行落点、重置落点、相机、碰撞覆盖层 | 混合：JSON 样例布局 + 实际碰撞、正确路由、防反弹、状态清理/相机限制 |
| `test_map_world.gd` 的模板身份/探索、脱树准备、无效配置、旧出口事件、注册表拒绝、跨房状态保留、暂停/失活阻止、能力门槛 | 机制；使用固定样例身份作为测试输入，失败原子性与状态前后关系不从业务生成预期 |
| `test_map_world.gd` 的三语 HUD/菜单与场景往返 | 机制 + 已交付 HUD 保留区布局；不评价译文风格或手感 |

当前整理只集中尺度/移动与样例地图布局。生命、技能、其他测试模块的独立规则仍由其模块文档与用例维护，未宣称全部设计数值已迁入这一份 JSON。测试创建的临时平台、顶板、输入帧数和安全偏移是受控夹具，不是新增玩法默认值。恒速采样在测试实例中移除 `Step` / `Platform` 障碍，避免获批提速后提前碰台阶导致速度用例误报；正式场景不改，独立的墙体、跳上台阶和碰撞断言继续运行。

## 有意调参 / 编辑地图的交接

1. **保留实际输入。** 调参或布局变化以已保存文件与 diff 为输入。若存在用户未保存或正在编辑的内容，先保存当前证据并避免覆盖这些文件；不能替用户 stash/reset。Agent 仍按既有 [worktrees.md](worktrees.md) 使用自己的隔离开发目录。本流程不新增固定的人类工作区、分支或项目。
2. **记录意图与输入。** 交接写明用户指令、目标参数/布局、旧值与新值、文件、工作区绝对路径和提交/补丁哈希。明确哪些是已批准变化，哪些仍是提案；不从聊天之外的旧快照猜批准范围。
3. **先执行原有验收。** 在已交接快照运行 `node tools/check.mjs --scope game`，读取原始 report、JUnit 和日志，保留设计预期与新实现不同造成的失败。不要先把用户值改回旧值，也不要先读取业务值覆盖 JSON。
4. **区分失败。** `DESIGN_BASELINE` 差异可能是有意调参，必须逐项对应用户指令。机制失败先查 [公共错误记录](errors/README.md)，再判依赖/环境/资源配置/代码/测试原因。只有有证据的夹具不再适配新速度或布局时才改测试操作；不删除碰撞、状态、合法性边界或放宽精度来掩盖缺陷。单看错误标签不能自动判原因。
5. **形成可审查修改。** 已批准的设计变化，在同一 PR 修改生产配置/场景、所属模块文档、JSON 中对应字段，以及本页后续变更记录。说明旧→新、授权出处、容差/夹具为何变化和影响到的 case。用户的新具体调参指令可作为批准，不重复索取许可；尚未批准的范围保持提案状态，不把基线写成已接受。
6. **复验与交付。** 先复跑原失败项及相关机制，再运行完整 game 入口。由测试 agent 读报告、主 agent 核原始数据；提交 PR 时写明基线变化与用户手感状态。通过必要验证后按项目持续提交与合并授权交付；提交与合并不代表用户已经验收手感。

机器/agent 交接至少保留以下字段，可存于本轮忽略的 `artifacts/`，但批准后的**持久设计变更记录应随 PR 提交到所属模块文档和下表**：

```json
{
  "change_id": "design-change-<task-id>",
  "request_source": "用户指令日期、原文或可访问引用",
  "authorization": "accepted | proposed",
  "checkout": "/absolute/checkout",
  "source_commit_or_patch_sha256": "完整提交或补丁哈希",
  "files": ["生产资源", "tests/baselines/design-v1.json", "模块文档"],
  "changes": [{"field": "unit_scale.walk_speed_px_per_second", "old": 56, "new": "用户明确值"}],
  "mechanism_cases_retained": ["相关稳定 test_name"],
  "fixture_or_tolerance_changes": "没有，或逐项原因",
  "before_run": {"run_id": "原失败轮", "report_path": "本 checkout 下报告"},
  "after_run": {"run_id": "完整复验轮", "report_path": "本 checkout 下报告"},
  "playtest": "pending | 用户反馈引用"
}
```

不能生成“将实际结果接受为新基线”的自动修复命令。此流程允许经批准的调整，也要求保留旧失败与新的回归证据。CI 不拥有玩法批准权。
