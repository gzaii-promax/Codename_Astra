# 第一版地图系统契约与后续事项

记录日期：2026-10-02。用户已采纳上一版全部建议并授权实现第一版地图系统。本文件记录已采纳结构、第一版验收和后续 TODO；交付验证以本轮实际报告与图形检查为准，不能由方案文档推定通过。

## 已采纳事项

- 以房间作为地图的基本制作单位，完整地图后续逐步扩展。
- 先实现 3 个灰盒房间小区域，采用 A ↔ B ↔ C 与 C → A 的单向返回路线，其中 A/C 复用同一模板，完整地图后续扩展。
- 转场与预加载均属于后续需要实现的功能，地图系统第一版可以暂缓，须保留扩展空间。用户已澄清原注释中的“预先”为“转场”的笔误。
- 攀爬属于后续需要实现的能力，作为技能方向扩展；第一版暂不实现，须保留扩展空间。
- 采用 Godot 原生编辑器制作地形和节点；按需求扩展工具，不在第一版开发完整独立编辑器。模板、世界房间身份、连接与会话状态分离，素材类型、格子位置、对象实例身份分开。

## 第一版范围与可观察验收

1. 正式主场景是三房间世界；保留训练场，通过菜单实际往返，并保持原生命、技能、多语言、尺度与跳跃回归。
2. A/C 共用 512 × 256 px 房间模板，B 是 768 × 256 px 大厅。地形为保存于场景的 TileMapLayer，入口、出口及边界能直接在 Godot 中编辑；共享 TileSet 有独立素材说明。
3. 独立资源注册 room_id、场景、标题与有向连接；正常移动触发真实出口，A/B 和 B/C 可往返，C/return 单向回 A/start，不自动生成反向连接。
4. 安全入口与触发区域分开；反复进入不反弹，场景之外准备不启动房间、不改变探索或玩家。无效 ID、资源或入口失败时保留原房间与玩家。
5. 玩家持续存在，正常切房保留生命、技能等级、剩余冷却与受击保护；结束当前动作，清空运动/跳跃锁存与旧攻击效果，不借切房补血或绕过冷却。
6. 相机 zoom=2，按房间边界夹取顶部 160 px HUD 之外的地图区域；真实碰撞、跳跃与台阶可达性另验。已有移动数值不因地图更大而擅自调整。
7. 探索记录按 room_id 独立，重访不重复。首版只维护当前地图会话；R、离开地图后重新进入、退出重启均开始新探索。没有磁盘存档或新增宝箱玩法。
8. 三语显示房间、探索与操作说明；暂停阻止通行，菜单重置有效；F3/F4/F5 调试跳到 A/B/C，F6 查看碰撞。实际画面与用户手感分别验收。

## 已采纳结构：房间、连接与状态

以下结构已获用户采纳；第一版实现边界以上述范围为准。

- 房间场景提供可复用的布局模板，世界中的房间使用独立的稳定 `room_id`。同一模板用于多个房间时，各自的连接与状态独立。
- 出口包含本房间内的标识和触发范围；入口包含标识、落点及朝向。出口触发区域与落点分开，防止进入后立即反向触发。
- 世界连接数据描述来源房间/出口、目标房间/入口。建议用有向关系表达，双向通道由两条关系组成；工具可提供一次创建双向连接的便利。
- 单向跌落、传送、同一房间多个入口、两个房间之间多条路线均可由该关系表达。第一版可先采用固定目标，剧情改道与多目标选择后续按需求扩展。
- 房间内持久对象使用 `room_id + object_id` 定位状态；瓦片类型、地图格子与对象实例的标识分别承担职责。运行状态不写回共享模板资源。
- 准备/加载房间与激活/进入房间划分职责，便于后续加入预加载。第一版 `prepare_room` 返回脱离场景树且禁用处理的房间，准备阶段不会启动物理或触发器；后台加载与缓存策略后续确定。
- 后续通行条件通过统一的能力/世界状态查询扩展。地图无需自行实现攀爬动作；实际地形仍需用角色移动能力验证。

## 已采纳制作流程与样例

- 建议先在 Godot 编辑器中绘制地形、摆放可复用场景并配置出入口，按实际制作需求增加总览、连接检查等插件功能。
- 编辑工具用于创建并保存关卡内容；运行时控制台用于跳转房间、显示碰撞、检查状态等调试操作。两者职责不同。
- 3 房间样例采用 `A ↔ B ↔ C`，另设 `C → A` 的单向路线，用于检查连接并非强制双向；A/C 复用同一模板，验证身份和状态独立。
- 样例优先验证真实通行、落点、相机及反复进出；不要求先齐备正式素材，也不代表已确定完整地图、存档或攀爬玩法。

- 第一版已实现；最终本地验收、原目录启动、三语与碰撞实际图形证据见 [当前交付状态](status.md)。用户手感与正式素材仍待验收。
